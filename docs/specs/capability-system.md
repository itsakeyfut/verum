# Capability system

Expressing in types what an endpoint, service or middleware is allowed to do.
Verum's core mechanism.

Related: [`handler-rules.md`](./handler-rules.md),
[`unverified-boundaries.md`](./unverified-boundaries.md),
[`rust-type-model.md`](./rust-type-model.md).

---

## The core idea

> Rather than explaining to an AI that something must not be done, **create a
> state where the call is a compile error.**

Not "you must not use this", but a type-level state in which it cannot be used.

> **On stating this accurately**: it is not that "the method does not exist". The
> setter is generated by the derive, so it does exist; what is unsatisfied is its
> where clause (E0277). rust-analyzer keeps completing it. The accurate guarantee
> is "**calling it does not compile**".

---

## Decision: capabilities are held by `Ctx<'req, Self>`

```rust,compile_fail
async fn handle(&self, req: Req, ctx: Ctx<'req, Self>) -> Result<Res> {
    let mut user = ctx.users().find(req.id).await?;
    ctx.users().set_email(&mut user, req.email)?;
    //  ^ where Self::Mutates: Has<Mutate<User, user::Email>, I>
    //    a type error here if it was not declared
}
```

### Why it carries a `'req` lifetime

`Ctx` is **bound to the request's lifetime.** It is not `'static`, so it cannot
be passed to `tokio::spawn`.

```rust,ignore   // fragment, not a complete item
tokio::spawn(async move { ctx.email().send(...).await });
//           ^^^^^^^^^^ error: `ctx` does not live long enough
```

That closes the following routes.

| Route | Why it is closed |
|---|---|
| Carrying a capability out of the request via `tokio::spawn` | `'static` is not satisfied |
| Handing it to a `static Sender<Ctx<E>>` and exercising it in a long-lived worker | Same |

**`Send` is preserved.** For the handler's future to load onto hyper's
multi-thread runtime it must be `Send`, so `Ctx` must be too. Dropping `'static`
alone achieves the goal.

> An invariant brand lifetime (the GhostCell approach) would seal the escape
> completely, but the error messages become extremely hard to read, colliding head
> on with [`diagnostics.md`](./diagnostics.md)'s goals. `'req` was judged
> sufficient.

### Provide an alternative route for spawning

Blocking it alone leaves the user with no way to avoid `tokio::spawn`. A
Verum-mediated spawn is provided.

```rust,ignore   // fragment, not a complete item
ctx.spawn::<SendEmailJob>(|jctx| async move { ... });
```

- Declaring the `Spawn<SendEmailJob>` effect is required
- The child task receives a **narrowed capability set**
- It appears in the contract, so it is traceable from the AI Context

**Removing "the easier unchecked route" requires providing a checked alternative
at the same time as blocking.**

### Seal the construction route

`Ctx`'s constructor requires a sealed `Runtime` token.

```rust,ignore   // fragment, not a complete item
impl<'req, E: Endpoint> Ctx<'req, E> {
    pub(crate) fn new(rt: &'req Runtime<Sealed>, ...) -> Self;
}
```

A user cannot construct a `Runtime<Sealed>`, so they cannot make a `Ctx` for an
arbitrary endpoint type.

This addresses **the god-mode test constructor problem.** Exposing
`Ctx::for_test()` would let a user define any `impl Endpoint` and construct a
`Ctx` holding every capability. `#[cfg(test)]` does not cross a crate boundary, so
a `test-util` feature enabled transitively survives into the production binary.

Testing is confined to an **API where the user cannot freely choose the endpoint
type.**

```rust,ignore   // fragment, not a complete item
verum::test::run::<UpdateUser>(req, mocks).await
```

### Rejected option: pass the capability as an explicit argument

```rust,ignore   // fragment, not a complete item
ctx.users().set_email(&mut user, req.email, caps.mutate::<user::Email>())?;
```

The information the explicit argument adds — `user::Email` — is **already obvious
from the name `set_email`.** It adds length without adding information.

And the explicit-argument design needs a separate mechanism tying an endpoint to
its repository, so the architecture-contract check described below does not come
for free.

The context-passing design does assume self-evidence is preserved. Its
preconditions are specified as the three rules in
[`handler-rules.md`](./handler-rules.md).

### Rejected option: express it as a trait bound

```rust,ignore   // fragment, not a complete item
async fn handle<C>(&self, req: Req, ctx: C) -> Result<Res>
where C: CanMutate<User, user::Name> + CanMutate<User, user::Email> + ...
```

The where clause duplicates the information already in the contract, violating a
single source of truth.

## Sealed traits — a precondition of any type-level guarantee

All of the following traits are **sealed** (they carry a private supertrait).

```text
Endpoint    ← a hand-written impl could declare any capability at all
Has         ← membership could be forged
Includes    ← impl Includes<Order> for User passes the orphan rule
Field       ← forging Field::NAME forges the column name in generated SQL
Condition   ← implementing a condition is allowed; forging the trait itself is not
ConsList    ← the shape proof could be forged, letting a malformed set pass as well-formed (T-M0-07)
Index       ← the position of membership could be forged (T-M0-07)
Append      ← the concatenation result could be forged; it has a `type Out`, so the combined set can be named (T-M0-09)
Lookup      ← "the entry for this key is this" could be forged, swapping out a conditional scope (T-M0-09)
```

> **This list was left un-updated three times running** (two were added by
> T-M0-07 and two by T-M0-09, and neither round was recorded here).
> **Sealing alone is not sufficient.** Unless the seal's solution set equals the
> trait's, the difference is forgeable — that shipped three times, in #6 / #8 / #9.
> The criterion and its mechanical enforcement are canonically in
> [`../rules/api-surface.md`](../rules/api-surface.md) §2. **When a new sealed
> trait is added, add it to this table too.**

```rust,ignore   // fragment, not a complete item
mod private { /* the seal! macro generates a per-trait seal */ }

pub trait Endpoint: derive_facing::SealedEndpoint { ... }
```

`Endpoint` is implemented only through the derive, which implements the private
marker.

### Why this is mandatory

By design, Verum **shows an AI a great many trait-bound errors.** And the first
fix an AI attempts against a trait-bound error is to **write the missing impl.**

```rust,compile_fail
// a "fix" an AI might make — this compiled before sealing
impl Includes<Order> for User {}   // ← the architecture contract disappears
```

`User` is a local type, so it passes the orphan rule, `cargo build` succeeds, and
the AI Context reports nothing. **One line voided the guarantee.** Today
`Includes` is sealed, so it is rejected with `E0277` (`spikes/doc-code-blocks`
verifies this on every run). The above records the state before sealing.

Sealing is a few lines of work, but **applying it later is a breaking change.** It
is mandatory for the First PoC.

> For `impl Has<Mutate<User, Password>> for ()`: `Has` and `()` are both foreign
> and `Mutate<User, ..>` is not a local type, so the orphan rule most likely
> prevents it (unverified). `Includes` definitely passes, though, so every trait is
> sealed without distinction.

## The capabilities an endpoint holds

```text
Endpoint<User, Update>
    ↓
Capabilities
    ├── Read<User, user::Status>
    ├── Mutate<User, user::Name>
    ├── Mutate<User, user::Email>
    └── Create<AuditLog>
```

An endpoint may be a **unit struct only.**

```rust,ignore   // needs a macro that arrives in M2
#[endpoint(PUT "/users/{id}")]
pub struct UpdateUser;          // ✅

#[endpoint(PUT "/users/{id}")]
```

```rust,compile_fail
pub struct UpdateUser { pool: PgPool }   // ❌ the derive errors
```

With fields, `self.pool` could run SQL directly and bypass ctx. This is the
condition that makes [`handler-rules.md`](./handler-rules.md) Rule 2 hold in
types.

## How it works: parameterise the repository's type by the contract

`Ctx` is a framework type, so domain-specific methods cannot be added by an
inherent impl (E0116). The derive generates an **extension trait** per domain.

```rust,ignore   // fragment, not a complete item
// derive-generated
pub trait CtxUsers {
    type R; type M;
    type Owner;                    // = the endpoint type (ADR-0002)
    fn users(&self) -> Repo<User, Self::R, Self::M>
    where Self::Owner: Includes<User>;   // ← the where goes on the method (note below)
}

impl<'req, E: Endpoint> CtxUsers for Ctx<'req, E> {
    type R = E::Reads;
    type M = E::Mutates;
    type Owner = E;
    fn users(&self) -> Repo<User, E::Reads, E::Mutates> { ... }
}
```

> **Important**: the where clause goes on the **method.** On the impl it becomes
> E0599 and `#[diagnostic::on_unimplemented]` is ignored. Detail in
> [`diagnostics.md`](./diagnostics.md).
> That `Includes`'s subject is the endpoint type, and that this is why the `Owner`
> associated type is needed, are in
> [ADR-0001](../adr/0001-includes-is-implemented-on-the-endpoint.md) and
> [ADR-0002](../adr/0002-ctxusers-exposes-the-endpoint-as-owner.md). **This section
> states the conclusion only and does not duplicate the reasoning.**

On an endpoint with `Mutates = ()` (a GET), the setter's where clause is
unsatisfied, so calling it is a compile error.

---

## A side benefit: the architecture contract holds at the same time

`ctx.users()`'s where clause requires `Self::Owner: Includes<User>` — that the
endpoint type declared `User` — so a repository for a domain not declared in the
contract **cannot be obtained.**

```rust,compile_fail
ctx.orders()
//  ^ type error: `Order` is not in this endpoint's domain contract
```

[`architecture-contract.md`](./architecture-contract.md)'s requirement therefore
holds through the same mechanism as the capability system. **No dedicated linter
is needed.**

### Propagation into the service layer

Passing a `dyn Repository` to a service erases the type parameters and loses the
capability constraint.

```rust,compile_fail
// ❌ allowing this lets the service call every setter
let svc = UserUpdateService::new(Arc::new(repo) as Arc<dyn UserRepository>);
```

**Do not expose `dyn Repository`.** What a service may receive is a parameterised
`Repo<D, R, M>`, and the service itself carries the capabilities in its type as
`Service<Reads, Mutates>`.

## What falls out of this design

| Item | How it holds |
|---|---|
| A GET's read-only guarantee | `Mutates = ()` → the setter's where clause is unsatisfied |
| MustNotMutate | Holds naturally as "no capability is issued for that field" |
| Field-level mutation | The domain is opaque and only per-field setters are provided |
| Restricting the read scope | The projection type is parameterised by `E::Reads` (Full PoC) |
| The architecture contract | `Includes<Domain>`'s where clause |
| The spawn boundary | `Ctx<'req, E>` is not `'static` |
| Most of effect inference | rustc does the matching of declared against implemented |

There is a limit to how far this reaches. **Every unchecked route is listed in
[`unverified-boundaries.md`](./unverified-boundaries.md).**

## Conditional capabilities

An effect permitted only under a condition has its capability issued only inside a
`ctx.when::<Cond>` scope.

```rust,ignore   // fragment, not a complete item
ctx.when::<EmailChanged, _>(&mut user, &req, async |ctx, user, req| {
    ctx.users().set_email(user, req.email.clone())?;
    ctx.events().emit(EmailVerificationRequested::for_user(user))?;
    Ok(())
}).await?;
```

**The closure's return type is fixed to `Result<()>`.** Otherwise `Ok(ctx)` would
carry the elevated context out of the scope.

```rust,compile_fail
let elevated = ctx.when::<C, _>(.., async |ctx, ..| Ok(ctx)).await?;
//                                                   ^^^^^^^ type error
```

Detail in [`conditional-effects.md`](./conditional-effects.md).

## Where capabilities come from

The intended structure is that authentication middleware issues capabilities,
which then flow to the endpoint.

```text
Authentication middleware
        ↓ issues capabilities
Endpoint<Effects, Capabilities>
        ↓ requested through Ctx<'req, Self>
Service / Repository
```

`tower::Service`'s types — request, response, error, and nothing else — cannot
express this. See [`middleware.md`](./middleware.md).

## A capability is not authorisation

**The misunderstanding most likely to cause an incident.**

```text
static capability (compile time) — "what can this endpoint do"
dynamic authorisation (run time) — "what is this caller allowed to do"
```

Capabilities cover only the former. **The latter is always needed separately.**

```rust,ignore   // needs a macro that arrives in M2
#[contract(domain = User, deletes = [User])]
pub struct DeleteUser;

impl Handler for DeleteUser {
    async fn handle(&self, req: Req, ctx: Ctx<'req, Self>) -> Result<()> {
        ctx.users().delete(req.id).await   // no authorisation check. It compiles
    }
}
```

The contract is complete, the compiler is satisfied, and the AI Context produces
tidy output. **And anyone can delete anyone else's account.**

Furthermore, `Mutate<User, user::Email>` means "the email column of the User type
may be written", not "**this** user may be written", so row-level permissions
(IDOR) are entirely invisible in the contract.

### What is done about it

- State [`../concepts.md`](../concepts.md)'s principle as "capability **and**
  permission checks"
- Consider requiring `authz` to be declared in the contract, with omission
  disallowed
- Emit `row_scope` in the AI Context as an unchecked boundary
  ([`unverified-boundaries.md`](./unverified-boundaries.md))

**The more complete a contract looks, the stronger the false assurance that it
covers everything.** That authorisation lies outside the contract is stated
plainly, not hidden.

## A design caution

Never expose an entry point like Axum's `State<AppState>`, from which anything can
be obtained. The capability system breaks at the root.

See [`runtime-stack.md`](./runtime-stack.md)'s Dependency Hiding Rule.
